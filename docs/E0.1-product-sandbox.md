# E0.1 — Can a Product reach a third-party origin?

**Status: GO** (2026-07-29) · desktop gateway only, see [Caveats](#caveats).

## Why this experiment exists

The push/tunnel architecture requires the game client to open a connection *out* to the
Acurast verifier. A Product is a static bundle running in a sandboxed cross-origin iframe
with all chain RPC routed through the host container — so it was an open question whether
arbitrary egress is permitted at all. If it is not, the entire transport has to be
rebuilt around a pull/oracle model.

This was sequenced first because it is a few hours of work and can invalidate everything
downstream.

### Third-party fetch — the decider

Egress to an arbitrary HTTPS origin **is permitted**. The `HTTP 400` is the DNS-over-HTTPS
endpoint objecting to the query format, which is the point: a CSP or sandbox block raises
a `TypeError` and never yields a status code at all. A response — any response — proves
the request left the sandbox.

**The push/tunnel transport is viable.** No pivot to pull/oracle needed.

### WebAssembly — the check that nearly got missed

This was not in the original plan and should have been. A CSP without `wasm-unsafe-eval`
would block `WebAssembly.instantiate` and kill the client-side simulation just as
completely as a blocked fetch — and unlike the fetch, there is **no fallback**: the whole
design rests on the client and the enclave running the same `sim.wasm`. It passes, so
`sim.wasm` (22 KB, from [E0.2](E0.2-determinism.md)) can run in the client.

### SharedArrayBuffer — a prediction confirmed

`crossOriginIsolated=false` and no `SharedArrayBuffer`, exactly as the plan predicted.
This is the concrete evidence for ruling out Godot and Bevy web builds: their threaded
targets need COOP/COEP response headers that **we do not control** — the gateway sets them,
not us. WebGL2 is hardware-accelerated, so PixiJS v8 is confirmed viable.

### The `injectedWeb3` warning is expected, not a problem

`window.injectedWeb3.spektr` is injected by **`@novasamatech/host-api-wrapper`, which is
product-side**, not pushed in by the host. A bare HTML page with no SDK will never see it.
The probe deliberately carries no dependencies, so its absence says nothing about wallet
availability. Signing gets exercised properly when the real client wires up
`@parity/product-sdk`.

## Reading the result

The gateway serves only Parity's **loader shell**. The Product is resolved entirely
client-side: smoldot light client → DotNS `contenthash` → Bulletin over Bitswap →
service-worker VFS → sandboxed iframe. So `curl` returns the shell and never the app.

**Automated testing therefore needs a headed browser.** The first attempt used headless
Chrome and failed — smoldot cannot peer without WebRTC:

```
bitswap_v1_get error: No Bitswap peers connected, can't issue "have" request
Smoldot has panicked ... panicked at wasm-node/rust/src/platform.rs:1035:37
```

That is a harness failure, not a result, and it would be easy to misread as "the gateway is
broken". The driver (`scratchpad/cdp-probe.mjs`) runs Chrome headed over CDP and attaches
to every target so it can reach the iframe's execution context.

## Caveats

**Only the desktop web gateway was tested.** The Android/iOS app uses a native platform
webview — a different engine with potentially different CSP and sandbox flags. The result
here is necessary but not sufficient.

To close that gap, open `rainbowprobe.dot` in the Polkadot app and compare; the probe
renders a machine-readable JSON blob at the bottom of the page for exactly this. Until
then, treat mobile as unverified rather than assumed-passing.

## What this unblocks

The plan's Phase 0 gate — "nothing in Phase 1+ starts until E0.1 and E0.2 are green" — is
now satisfied on desktop. Remaining Phase 0 work is [E0.3](../docs/) (`signer_sign`
round-trip, which decides the contract's digest construction) and E0.4 (Cloudflare Tunnel
from a Shell job).
