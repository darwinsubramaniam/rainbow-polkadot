# E0.3 / E0.4 — Acurast signing semantics and tunnel

**Status: both PASS** (2026-07-29), deployment `380395` on Acurast Canary.

## E0.3 — What does `signer_sign` do with its input?

### Why it mattered

EIP-712 requires a signature over `keccak256(0x1901 ‖ domainSeparator ‖ structHash)`. If
the runtime hashes its input first, the Solidity side has to compensate. Get it wrong and
you ship a contract that compiles, deploys, and then **silently rejects every attestation
forever** — there is no error to observe, only a leaderboard that never updates.

The Node.js runtime is documented to force an envelope
(`keccak256("acusig" ‖ SCRIPT_HASH ‖ msg)`), which would break `_hashTypedDataV4` recovery
outright. The Cargo/Shell runtime's `signer_sign` is documented as signing "a hex-encoded
byte string" with no stated envelope — but documented and actual are not the same thing,
so this was settled by experiment.

### Result

```
CONCLUSION : signer_sign signs the input bytes directly as a pre-computed digest
SIG LAYOUT : r||s  (64 bytes)
NONCE      : deterministic (RFC 6979)
```

**Goal.md §5/§7 stands unchanged.** The enclave computes the EIP-712 digest, passes those
32 bytes to `signer_sign`, and the contract verifies with
`ECDSA.recover(_hashTypedDataV4(structHash), sig)`.

**One required adaptation:** `signer_sign` returns **64 bytes (`r‖s`)**, but
`ECDSA.recover` needs 65 with a recovery id. The job must recover `v` itself — try both
recovery ids and keep the one that yields the deployment's own address — then append it.
Note OpenZeppelin's `ECDSA` expects `v ∈ {27, 28}`, not `{0, 1}`.

A 5-byte input also signed and recovered *without* hashing, so the runtime pads short
input to 32 bytes rather than hashing it. Consistent with the 32-byte result.

### The key is verifiable on-chain — a real strengthening of the design

The signing key matched the key published on-chain in the deployment's assignment,
**before the job ran**:

| Source | secp256k1 |
|---|---|
| on-chain (`storedMatches`, job 380395) | `0x020e78df…761976` |
| reported by the enclave | `020e78df…761976` |
| → Ethereum address | `0xda48e2c72e70cdb28e18d69261dcbce91f7798b8` |

So the contract's expected signer is **derivable from chain state**, not asserted by
whoever deployed the job. `setVerifier` stops being "trust the operator's claim about
which key lives in the enclave" and becomes a value anyone can independently confirm.
Goal.md §7 lists `setVerifier` as the single point of compromise; this narrows it
materially.

Keys are **per deployment**: job 380393 had `0x2804da09…`, job 380395 has `0xda48e2c7…`.
Every redeploy mints a new verifier address unless `reuseKeysFrom` is used, which requires
the prior deployment to be `mutability: "Mutable"`.

## E0.4 — Can a Shell job serve HTTPS a browser accepts?

**Yes, via a Cloudflare quick tunnel** — no Cloudflare account, no DNS, no token:

```
https://incorporated-reservoir-josh-tennis.trycloudflare.com
  /health -> HTTP 200 in 402ms
  /keys   -> HTTP 200 in 304ms
```

300–400 ms round trip from a laptop to a phone in SG. Combined with E0.2's ~22 ms replay
cost, a claim is comfortably sub-second on the network path.

**Trust cost, stated plainly:** Cloudflare terminates TLS and therefore sits in the
attestation path. It **cannot forge an attestation** — the payload is signed by a key
inside the processor's secure element whose public half is on-chain — so it is a liveness
and censorship dependency, not an integrity one.

**The native Acurast tunnel is now a viable alternative.** The plan chose Cloudflare
because `tunnel_*` needs build 122, which a May snapshot measured at ~7 devices
network-wide. Since then 1.26.0 shipped stable as **build 128**, and the deployer account
(`5FcZAi77…KTsJ`) already has a verified `_acu.tunnel.dw3labs.work` TXT record from the
earlier testAcurast work. Switching removes Cloudflare from the path entirely; worth doing
before the grant writeup.

## What it cost to get here — three failed runs

Worth recording, because each failure was a category of mistake rather than a typo.

| Run | Failure | Cause |
|---|---|---|
| 380393 | died silently, ~2 min in | `usageLimit` misread as a cap; **no diagnosis possible** |
| 380394 | `cp X X` | bundle extracts to `/root/app`, which *is* `$HOME/app` |
| 380395 | — | passed |

**`usageLimit` is a requirement matched against the processor's advertisement, not a cap
on consumption.** Asking for `memory: 1000000000` against an advertised `20000` makes the
device ineligible. The on-chain types settle the units question: the advertisement is
`{maxMemory u32, networkRequestQuota u8, storageCapacity u32}` — and a `u8` cannot hold a
byte count, so `networkRequestQuota` is a *request count*. The docs' "(in bytes)" is
wrong. `storage` is also priced (`base + perMs×duration + perByte×storage`).

**The deeper failure was having no channel.** `acurast devtools` resolves against
**mainnet**, so a Canary job has no stdout at all — anything not POSTed is lost. Run 1
combined that with `set -e` and stdout-only error paths, guaranteeing a mystery. The fix:
install `curl` first, POST every step, and add an EXIT trap posting the exit code plus a
log tail. Run 2 then reported its cause in one line.

Full catalogue of PRoot gotchas is in the vault:
`resources/acurast/Acurast — Shell (Cargo) Deployments: Config, Limits & Debugging`.

## Consequences for the contract

1. Keep EIP-712 exactly as Goal.md §5 specifies.
2. The enclave must append a recovery id to `signer_sign`'s 64-byte output, normalised to
   `v ∈ {27, 28}`.
3. `isVerifier` entries can be **derived from chain state** rather than trusted — worth
   asserting on-chain at registration time.
4. Every redeploy rotates the verifier key unless `reuseKeysFrom` is used, so keep
   `isVerifier` a set and add without removing, as planned.
