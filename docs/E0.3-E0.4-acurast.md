## E0.3 — What does `signer_sign` do with its input?

### Why it mattered

EIP-712 requires a signature over `keccak256(0x1901 ‖ domainSeparator ‖ structHash)`. If
the runtime hashes its input first, the Solidity side has to compensate. Get it wrong and
you ship a contract that compiles, deploys, and then **silently rejects every attestation
forever** — there is no error to observe, only a leaderboard that never updates.

The Node.js runtime is documented to force an envelope
(`keccak256("acusig" ‖ SCRIPT_HASH ‖ msg)`), which would break `_hashTypedDataV4` recovery
outright. The Cargo/Shell runtime's `signer_sign` is documented as signing "a hex-encoded
byte string" with no stated envelope — but documented and actual are not the same thing,
so this was settled by experiment.

### Result

```
CONCLUSION : signer_sign signs the input bytes directly as a pre-computed digest
SIG LAYOUT : r||s  (64 bytes)
NONCE      : deterministic (RFC 6979)
```

**Goal.md §5/§7 stands unchanged.** The enclave computes the EIP-712 digest, passes those
32 bytes to `signer_sign`, and the contract verifies with
`ECDSA.recover(_hashTypedDataV4(structHash), sig)`.

**One required adaptation:** `signer_sign` returns **64 bytes (`r‖s`)**, but
`ECDSA.recover` needs 65 with a recovery id. The job must recover `v` itself — try both
recovery ids and keep the one that yields the deployment's own address — then append it.
Note OpenZeppelin's `ECDSA` expects `v ∈ {27, 28}`, not `{0, 1}`.

A 5-byte input also signed and recovered *without* hashing, so the runtime pads short
input to 32 bytes rather than hashing it. Consistent with the 32-byte result.

### The key is verifiable on-chain — a real strengthening of the design

The signing key matched the key published on-chain in the deployment's assignment,
**before the job ran**:

| Source | secp256k1 |
|---|---|
| on-chain (`storedMatches`, job 380395) | `0x020e78df…761976` |
| reported by the enclave | `020e78df…761976` |
| → Ethereum address | `0xda48e2c72e70cdb28e18d69261dcbce91f7798b8` |

So the contract's expected signer is **derivable from chain state**, not asserted by
whoever deployed the job. `setVerifier` stops being "trust the operator's claim about
which key lives in the enclave" and becomes a value anyone can independently confirm.
Goal.md §7 lists `setVerifier` as the single point of compromise; this narrows it
materially.

Keys are **per deployment**: job 380393 had `0x2804da09…`, job 380395 has `0xda48e2c7…`.
Every redeploy mints a new verifier address unless `reuseKeysFrom` is used, which requires
the prior deployment to be `mutability: "Mutable"`.

## E0.4 — Can a Shell job serve HTTPS a browser accepts?

**Yes, via a Cloudflare quick tunnel** — no Cloudflare account, no DNS, no token:

```
https://incorporated-reservoir-josh-tennis.trycloudflare.com
  /health -> HTTP 200 in 402ms
  /keys   -> HTTP 200 in 304ms
```

300–400 ms round trip from a laptop to a phone in SG. Combined with E0.2's ~22 ms replay
cost, a claim is comfortably sub-second on the network path.

**Trust cost, stated plainly:** Cloudflare terminates TLS and therefore sits in the
attestation path. It **cannot forge an attestation** — the payload is signed by a key
inside the processor's secure element whose public half is on-chain — so it is a liveness
and censorship dependency, not an integrity one.

**The native Acurast tunnel is now a viable alternative.** The plan chose Cloudflare
because `tunnel_*` needs build 122, which a May snapshot measured at ~7 devices
network-wide. Since then 1.26.0 shipped stable as **build 128**, and the deployer account
(`5FcZAi77…KTsJ`) already has a verified `_acu.tunnel.dw3labs.work` TXT record from the
earlier testAcurast work. Switching removes Cloudflare from the path entirely; worth doing
before the grant writeup.

### Superseded by a named tunnel (2026-07-30, deployment `380403`)

The quick tunnel is gone. The phone now attaches as a connector to a **named** tunnel we
own, so the hostname lives in Cloudflare rather than in the job and survives a restart or a
reassignment to another processor:

```
https://rainbow-verifier.dw3labs.work   /health -> 200 in ~330ms
```

That is what makes a build-time constant in the app worth having; `app/src/Play.tsx` no
longer carries a per-run `*.trycloudflare.com` literal that goes stale the moment its job
ends.

**A named tunnel must stay single-connector.** Cloudflare treats every connector on a
tunnel as an interchangeable replica and round-robins between them. For a stateless site
that is free redundancy; here it is a correctness bug, because every deployment mints its
own key, so a second connector would sign some fraction of attestations with a key the
client never pinned. `numberOfReplicas` stays 1, and `lib/tunnel.sh` asks the public
hostname for its `/identity` at boot and withdraws if the answer is not its own. On 380403
that check passed on its first real run.

The three-way agreement this buys is the point:

| Source | secp256k1 |
|---|---|
| on-chain assignment, job 380403 | `032cd907…e418e9` |
| the enclave's own `/identity` | `032cd907…e418e9` |
| the public hostname | `032cd907…e418e9` |
| → registered verifier | `0xce0d7dfaf3b8d377ced5ba25cb47f26d192e75d2` |

## Reproduce

The original signing probe (this is the experiment whose `server.py` really does serve
`/report`):

```bash
cd e2e/experiments/e0.3-signer-semantics
cp .env.example .env          # add ACURAST_MNEMONIC (cACU funded)
node verify.mjs --selftest    # validate the detector FIRST
acurast estimate-fee e0-signer
acurast deploy e0-signer
sh pull-report.sh             # newest report from the sink -> verify.mjs
```

The verifier itself. Run the harness before spending a deploy — it exercises the whole
entrypoint in ~40s, against a phone's ~2m20s just to reach the first breadcrumb:

```bash
cd acurast-verifier/local-test && ./run.sh --smoke   # exits 0 on reaching serve

cd .. && acurast deploy rainbow-verifier                 # note the deployment id

# read the deployment's key from chain state — NOT from the enclave's own claim
acurast deployments <id>                                 # -> SECP256k1 in the assignment

cd ..                                                    # helper scripts are root-relative
node scripts/revive-call.mjs --to $CONTRACT \
  --data "$(cast calldata 'setVerifier(address,bool)' $ENCLAVE_ADDR true)" --dry-run
```

**What the harness cannot tell you.** It reproduces the shell logic, the missing curl/node,
the TMPDIR leak and the `/root/app` layout — not the proot/Android specifics: the netlink
ban, blocked `/proc/net`, the network namespace shared across jobs, or the real secure
element. A green smoke run means the script is sound, not that the job will run.

## What it cost to get here — three failed runs

Worth recording, because each failure was a category of mistake rather than a typo.

| Run | Failure | Cause |
|---|---|---|
| 380393 | died silently, ~2 min in | `usageLimit` misread as a cap; **no diagnosis possible** |
| 380394 | `cp X X` | bundle extracts to `/root/app`, which *is* `$HOME/app` |
| 380395 | — | passed |

**`usageLimit` is a requirement matched against the processor's advertisement, not a cap
on consumption.** Asking for `memory: 1000000000` against an advertised `20000` makes the
device ineligible. The on-chain types settle the units question: the advertisement is
`{maxMemory u32, networkRequestQuota u8, storageCapacity u32}` — and a `u8` cannot hold a
byte count, so `networkRequestQuota` is a *request count*. The docs' "(in bytes)" is
wrong. `storage` is also priced (`base + perMs×duration + perByte×storage`).

**The deeper failure was having no channel.** `acurast devtools` resolves against
**mainnet**, so a Canary job has no stdout at all — anything not POSTed is lost. Run 1
combined that with `set -e` and stdout-only error paths, guaranteeing a mystery. The fix:
install `curl` first, POST every step, and add an EXIT trap posting the exit code plus a
log tail. Run 2 then reported its cause in one line.

Full catalogue of PRoot gotchas is in the vault:
`resources/acurast/Acurast — Shell (Cargo) Deployments: Config, Limits & Debugging`.

## A second round of silent runs — 380401, 380402 (2026-07-30)

Two deployments went out and reported **nothing at all**, on a phone whose heartbeat was
healthy and whose build (128) met the minimum. They cost most of a day, and almost all of
that was spent measuring the wrong things. Recorded because the wrong turns are the
reusable part.

### What the silence was not

| Suspected | Actually |
|---|---|
| the hostname was dead (`HTTP 000` from a poll) | a stale **negative DNS cache**: `dig` resolved fine while `curl` said "could not resolve". The poll was reporting a lookup failure as an origin failure. |
| `Assignments: []` meant the processor was deassigned | that is what **every** started job looks like, including 380397 which ran a full healthy hour. The stored match is cleared at execution start. |
| a ~20-minute stale `processorHeartbeat` meant the phone was offline | the heartbeat cycle is ~30 minutes. The phone was fine throughout. |
| the Cloudflare config was wrong | `error 1033` / HTTP 530 means the route exists and no connector is attached — i.e. the job never got that far. The config was correct all along. |

Useful chain-state reads while diagnosing, none of which the CLI surfaces:

```
acurastMarketplace.storedJobStatus(jobId)          -> {"assigned":1} while held
acurastMarketplace.storedJobExecutionStatus(...)   -> "Open" until an execution is reported
acurastMarketplace.nextReportIndex(jobId, proc)    -> empty if the processor never reported
acurastProcessorManager.processorHeartbeat(proc)   -> ~30 min cycle
acurastProcessorManager.processorVersion(proc)     -> {"platform":0,"buildNumber":128}
```

### The blind window, and what was done about it

`start.sh` cannot report before curl exists, because curl is the thing that reports. Every
failure in that window is therefore indistinguishable from a phone that never started the
job. Three changes narrow it:

1. **Every apt call is bounded** (`timeout`, plus `Acquire::*::Timeout`), so a hang becomes
   a fast failure that frees the assignment instead of consuming the whole execution
   window in silence. Measured: a hanging apt now aborts in ~28s instead of 300s+.
2. **A `preflight` breadcrumb** posts the moment curl exists, reconstructing the window
   after the fact — per-try exit codes (124 = timed out), elapsed seconds, and which env
   vars arrived. By name only: `CF_TUNNEL_TOKEN` is a credential and the line goes over the
   wire.
3. **A local Docker harness** (`acurast-verifier/local-test/`) that starts from an
   image with *no curl and no node*, because that emptiness is the part that keeps failing.
   `./run.sh --smoke` runs the whole checklist to the serve loop and exits 0/1/2 for CI.

When 380403 finally spoke, the answer was anticlimactic and worth writing down:

```
preflight  curl after try1(update=0 install=0 at=98s) total=98s; env: … all set
```

apt succeeded on the **first try**. Whatever killed 380401 and 380402 was not apt, and is
still unexplained — the fix made the window legible, it did not explain the earlier runs.

### The `/report` step never worked

`post_report` fetched `http://127.0.0.1:$PORT/report` and reported success on any non-empty
response. `verifier.mjs` does not serve `/report` — its routes are `/health`, `/identity`,
`POST /session`, `POST /attest` — so it was posting a 404 body every time. The step was
inherited from the E0.3 probe, whose `server.py` genuinely does serve `/report`.

This went unnoticed because run 380397, treated as the healthy baseline all day, posted
exactly **68 bytes** to `/report` — the length of that error body. The step is removed.

> **A check whose success condition is "the response was not empty" will pass on an error
> page.** If a report step returns, it must assert on the *shape* of what it got.

### The verifier key tracks the bundle, not the deployment

Recorded here because this file previously said the opposite, and the difference decides
whether a redeploy costs an on-chain transaction.

Four consecutive deployments to the same processor:

| Job | Bundle (IPFS) | Verifier address |
|---|---|---|
| 380401 | `QmQyPAef…` | `0x4b60d4f9…` |
| 380402 | `QmfWusQL…` | `0x2c6c6a5f…` |
| 380403 | `QmaKwfk9…` | `0xce0d7dfa…` |
| 380404 | `QmaKwfk9…` | `0xce0d7dfa…` |

**Same bundle, same key.** 380404 redeployed 380403's bytes unchanged and got the same
secp256k1 back, so its `isVerifier` entry was already true and the redeploy needed no
transaction at all. The three earlier jobs each shipped a different bundle and each got a
different key.

So the operational rule is:

> `setVerifier` is needed when the **verifier bundle changes**, not every time you deploy.
> Editing `start.sh` or any `lib/*.sh` rotates the address; redeploying identical bytes
> does not.

That makes iterating on a *running* verifier much cheaper than assumed — but it also means
a one-character change to a shell script silently invalidates the registration, which is
the direction that fails closed and is worth remembering before a demo.

Two caveats, stated because this is measured rather than documented behaviour. It is
inferred from four samples on one processor, so whether the derivation also keys on the
processor is untested — a different phone may well produce a different address for the
same bundle. And it sits oddly beside `reuseKeysFrom` existing at all, which implies keys
are *not* normally stable across deployments. Read the key from the assignment and compare
before assuming either way; it is one CLI call:

```bash
acurast deployments <id>        # -> SECP256k1 in the assignment
```

Note `acurast.json` now sets `mutability: "Immutable"`, so `reuseKeysFrom` is unavailable
as a deliberate mechanism regardless.

### DevTools may no longer be mainnet-only

The note above that `acurast devtools` resolves against mainnet predates CLI 0.10, which
now prints a **Canary** deployment a DevTools URL with a 24h view key. Whether it actually
streams a Canary job's stdout is **unverified** — it would have shortened this debugging
session considerably, so it is worth testing. Note `enableDevtools: false` in
`acurast.json` suppresses the URL entirely.

## Consequences for the contract

1. Keep EIP-712 exactly as Goal.md §5 specifies.
2. The enclave must append a recovery id to `signer_sign`'s 64-byte output, normalised to
   `v ∈ {27, 28}`.
3. `isVerifier` entries can be **derived from chain state** rather than trusted — worth
   asserting on-chain at registration time.
4. The verifier key tracks the **bundle**, not the deployment — see below. Keep `isVerifier`
   a set and add without removing, as planned.

Phase 0 is complete on the questions that could invalidate the architecture. Two
narrow gaps remain, both recorded rather than assumed away: the Android/iOS webview, and
running `sim.wasm` through `wasmi` on the phone itself — the latter now cheap to close,
since a Shell job with a working tunnel is exactly the harness for it.

A third is now open, and it is operational rather than architectural: **two deployments
died before producing a single breadcrumb and that has never been explained.** 380403 boots
in ~2m20s with apt succeeding first try, so it is not a slow or failing apt. Until the
cause is known, treat a deploy as something that can silently not happen, and check the
sink rather than assuming.
