# E0.2 — Cross-target determinism

**Status: PASS** (2026-07-29) · one arm still outstanding, see [Residual risk](#residual-risk).

## Why this experiment exists

The replay guarantee is worth exactly as much as the simulation's determinism. If the
browser and the enclave disagree by a single point, the enclave refuses to attest a score
the player legitimately earned — an honest player is flagged as a cheat, with no error
message anywhere in the system. There is no runtime signal for this failure; it just looks
like the player is lying.

`Goal.md` §10 names this as the place the project quietly fails, and puts it first in the
build order. This is that check.

## What was tested

Three execution arms, compared **per tick** rather than on final score. A final-value
comparison would report *that* something went wrong but never *where*, and would miss a
divergence that happens to reconverge.

| Arm | Engine | Stands for |
|---|---|---|
| native | `sim` linked directly, aarch64/macOS | catches platform dependence in the *source* |
| wasmi | `sim.wasm` via `wasmi` 1.1.0 interpreter | **what the TEE verifier runs** |
| V8 | same `sim.wasm` via Node 26.5 / V8 14.6 | **what the player's browser runs** |

The wasmi↔V8 pair is the one that matters — that is literally enclave-versus-browser. The
native arm is a supporting check for source-level portability.

## Results

```
native vs wasmi     512 seeds · 3,369,299 ticks · identical per-tick state hash
wasmi  vs V8         48 vectors ·   372,631 ticks · identical score, state hash, run length
rejection paths       5 malformed log classes · all three arms agree
```

Reproduce:

```bash
cargo build -p sim-wasm --release --target wasm32-unknown-unknown
cargo run   -p replay   --release -- compare --seeds 512   # native vs wasmi
cargo run   -p replay   --release -- export  --seeds 48    # golden vectors
node harness/run-node.mjs                                  # wasmi vs V8
cargo run   -p replay   --release -- selftest              # negative control
```

### The negative control matters

A harness that only ever prints PASS looks identical whether it is checking carefully or
not checking at all. `replay selftest` injects a known one-bit divergence and asserts the
detector finds it, at the correct tick:

```
baseline: 7302 ticks agree
injected 1-bit fault at tick 3651: detected at 3651
injected truncation (7301 vs 7302 ticks): detected by length check
score comparison is live
```

**A green `compare` only means something if `selftest` is also green.** Run both.

## Cost to the enclave

Measured on the verify path (no per-tick hashing — that is harness-only):

| Metric | Value |
|---|---|
| Per claim, 11,753-tick run | **22.4 ms** |
| Throughput | ~524,000 ticks/sec |
| Extrapolated full 36,000-tick run | ~69 ms |
| `sim.wasm` size | **22,820 bytes** |

Two things follow. `Goal.md` §8's claim that a full run replays in "well under a second on
a processor phone" looks sound — even a 10× slower device lands near 0.7 s. And the 22 KB
module sits far below the ~1 MB Acurast bundle ceiling documented in the
`acurast-nextjs-deploy` skill, so the verifier bundle has ample headroom.

These numbers are an **upper bound**: measured on Apple silicon, not on a processor phone.
Re-measure on device before setting the per-player rate limit (defect D4).

## Design decisions this validated

- **One artifact, not two.** Both sides run the identical `.wasm`, so there is no cross-ISA
  arithmetic to reconcile — the comparison is between two *interpreters of the same
  bytecode*, which is a far weaker assumption than two ports agreeing.
- **`#![no_std]` with zero dependencies.** This makes `HashMap` iteration order,
  `SystemTime`, and thread-local RNGs unreachable rather than merely discouraged. It is
  structural enforcement of `Goal.md` §8 instead of a documentation convention.
- **D2 confirmed.** The in-tree `Pcg32` replaces `SmallRng`, which `rand` declines to
  guarantee across versions and which has historically varied by pointer width — exactly
  the wasm32 (32-bit) versus aarch64 (64-bit) split this system spans. A pinned golden
  vector in `crates/sim/src/rng.rs` now fails loudly if the generator ever changes.
- **No `usize` in `State`.** Enforced by a size/alignment assertion, since `usize` is
  32-bit on wasm32 and 64-bit on aarch64 and would silently desynchronise the state hash.

## Residual risk

**The on-device arm has not been run.** Everything above executed on Apple silicon. The
processor phone would run the same `sim.wasm` through `wasmi` on aarch64-Linux.

Residual risk is low — `wasmi` is a pure-Rust interpreter, the simulation contains no
floating point, and the module is byte-identical — but it is not zero, and this document
should not be read as saying the phone arm passed. Fold it into E0.4, which needs a live
Shell job anyway.
